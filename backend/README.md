## Purpose

This folder contains the conventional Django `startproject config` and `startapp dashboard` structure. We preserve the comments and headings generated by Django 5.2.x and make only the small changes needed for a **real**, renderable first application. Django's built-in admin/auth/session/staticfiles configuration remains intact. We add no third-party Django dependencies.

The public GitHub Pages site remains in the repository root and **does not serve this Python backend**. Development routes are for **local testing only**.

## Guided installer with Python selection

The optional [local installer](INSTALLER.md) discovers installed Python
interpreters, shows compatible versions and their paths, and lets you select
one interactively. Use `python3 backend/scripts/setup_local.py` from the
repository root (or `py -3.13 backend/scripts/setup_local.py` on Windows).
It uses only `backend/.venv`, calls the existing verifier and reports the first
failed stage. The manual setup instructions below remain available.

## Set up on Linux

From the repository root:

```bash
cd backend
python3.13 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt

# This example creates an ephemeral development key for this shell session.
# Use a persistent, securely stored key for any non-disposable environment.
export DJANGO_SECRET_KEY="$(python -c 'import secrets; print(secrets.token_urlsafe(50))')"
export DJANGO_DEBUG=1
export DJANGO_ALLOWED_HOSTS=127.0.0.1,localhost

python manage.py check
python manage.py migrate
python manage.py test
python manage.py runserver 127.0.0.1:8000
```

Navigate to http://127.0.0.1:8000/ (the Django landing page), or http://127.0.0.1:8000/admin/ (Django's built-in admin). The `repositories` app has one project-owned database model. `migrate` applies Django's standard migrations plus `repositories/0001_initial.py`. Create a local admin account with `python manage.py createsuperuser` to enter and inspect inventory records.

**No inbound port forwarding is necessary** to run these local development steps.

## Set up on Windows PowerShell

From the repository root:

```powershell
cd backend
py -3.13 -m venv .venv
.\\.venv\\Scripts\\Activate.ps1
python -m pip install -r requirements.txt

$env:DJANGO_SECRET_KEY = python -c "import secrets; print(secrets.token_urlsafe(50))"
$env:DJANGO_DEBUG = "1"
$env:DJANGO_ALLOWED_HOSTS = "127.0.0.1,localhost"

python manage.py check
python manage.py migrate
python manage.py test
python manage.py runserver 127.0.0.1:8000
```

A sample `.env.example` describes the variables, but **Django does not read it automatically**. The commands above set environment variables directly; no `python-dotenv` or additional dependency is required.

## Routes and tests

| URL | Source | Status |
| --- | --- | --- |
| `/` | `dashboard.urls` → `dashboard.views.home` | Template-only landing page |
| `/admin/` | `django.contrib.admin` | Standard Django admin with default authentication |
| `/repositories/` | `repositories.urls` → `repositories.views.repository_list` | Staff-only local inventory; no GitHub requests |

The original `SimpleTestCase` checks verify the home template/content and admin login redirect. Separate `repositories/tests.py` database tests cover model validation, the empty state, staff access, and denial for anonymous/non-staff users.

Run `python manage.py makemigrations --check --dry-run` to verify migration consistency, followed by `python manage.py test`.

### Read-only preflight (no Django or AI tokens)

The standard-library environment diagnostic only checks for Python 3.13, a Django import and `git`/`codex`/`claude` commands on PATH. It **does not run any CLI**, contact GitHub, validate credentials or inspect subscription quotas:

```bash
python scripts/preflight.py
python scripts/preflight.py --json
python -m unittest discover -v -s scripts -p 'test_preflight.py'
```

The JSON form is useful for future local tooling. Seeing a CLI on PATH is **not** permission to use it, proof of authentication, or approval of agent execution.


**Repeatable validation without GitHub Actions:** run `python scripts/verify.py` for standard-library syntax/structure checks. After installing Django, run `python scripts/verify.py --full` to perform Django `check`, migration drift detection, local `migrate`, and the test suite. See [the validation log](VALIDATION.md) for the exact evidence and current blockers. **Validation status:** `check`, `migrate`, `test`, and browser rendering still require a Python environment with Django installed; the scaffold has not passed these runtime gates yet. Run `python manage.py check --deploy` **only as a diagnostic** before attempting any deployment; the foundation is not production-ready.

The dependency range permits later security patch releases within Django 5.2 LTS, and its minimum is set to **5.2.19** (security release of 3 November 2026). The boilerplate header in `settings.py` intentionally records the **5.2.8** template version used to generate the original scaffold; a maintenance upgrade does not replace its vanilla comments.

## Vanilla conventions and deviations

All generated project files retain their standard names, ordering and Django-generated comments. `dashboard/admin.py` and `dashboard/models.py` remain intentionally empty apart from conventional imports and placeholder comments. The new `repositories` app uses the standard Django app file layout and has its own initial migration.

The deliberately small deviations are:

- `settings.py`: reads `DJANGO_SECRET_KEY` (required), `DJANGO_DEBUG` (defaults off) and `DJANGO_ALLOWED_HOSTS`; registers `dashboard.apps.DashboardConfig`.
- `config/urls.py`: adds the root URL include.
- `dashboard/urls.py`, a short view, a template and a test: make the first app usable and verifiable.

Settings register the additional `repositories` app while preserving Django's generated settings sections and comments. They retain **SQLite as Django's development default**. We will decide durable runtime storage later, instead of prematurely adding PostgreSQL/Redis/Docker to an empty scaffold.

## Local repository inventory

This is the first small application feature toward FR-01; it **does not implement authorisation for agent execution**.

1. Run `python manage.py migrate` in a local Django environment.
2. Run `python manage.py createsuperuser` and log in at `http://127.0.0.1:8000/admin/`.
3. Add a record under **Repositories** using a GitHub `owner/repo` name, optional description and inventory status.
4. Open `http://127.0.0.1:8000/repositories/` to browse the records. Only authenticated, active staff users can access the page.

Inventory statuses (`candidate`, `tracked`, `archived`) are **descriptive only**. Marking a repository as tracked does not authorise cloning, execution, data access, or use by an agent. No GitHub token or API call is required. Do not enter confidential repository identifiers in an environment exposed to unauthorised users.

The Django page loads the existing public Glassmorphism Pro theme stylesheet. The public GitHub Pages demo is unchanged and cannot read the local SQLite inventory.

## Shared frontend templates

Django's existing `TEMPLATES` configuration now includes `BASE_DIR / 'templates'` for shared layouts while leaving `APP_DIRS=True` unchanged. Both views extend `backend/templates/base.html`, and reusable navigation, status and footer sections live in `backend/templates/partials/`. The UI-specific stylesheet lives at `backend/dashboard/static/dashboard/css/app.css`, keeping Glassmorphism Pro upstream untouched.

See [frontend architecture](../docs/FRONTEND.md) for layout blocks, static asset order, accessibility rules and adding future pages. The responsive appearance still needs live browser inspection once Django can be run locally.

## Security and next steps

- No credentials, real agent jobs, private audit records or authorization payloads belong in this **public** repository.
- No server is being installed, no autonomous job execution is activated, and the public Pages interface remains fictional.
- Django's `runserver` is a **development server**, not a secure production deployment server. Bind it to loopback during this phase.
- Later Issues/PRs should decide login, private audit views, worker integration, GitHub bridge, database lifecycle, secrets management and deployment separately.

See the [documentation foundation PR](https://github.com/Vgarcan/dev-coordinator-hub/pull/7) for the proposed PDD, collaboration and security context. That PR is intentionally not a dependency of this scaffold.
